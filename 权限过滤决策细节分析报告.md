## 1. 分享操作（Share）的处理链路

### 1.1 分享权限的核心处理函数

**文件**: `api/src/permissions/utils/get-permissions-for-share.ts`

分享操作的权限处理是 Directus 中最复杂的场景之一，因为它涉及**双重权限验证**：
- 分享创建者的权限
- 分享指定角色的权限

#### 1.1.1 核心处理流程

```
分享令牌 (share token)
    ↓
fetchShareInfo()  → 获取分享信息
    ├── collection: 目标集合
    ├── item: 具体项目 ID
    ├── role: 分享指定的角色
    └── user_created: 分享创建者
    ↓
构建两个 accountability
    ├── userAccountability: 分享创建者的身份
    └── shareAccountability: 分享角色的身份
    ↓
并行获取权限
    ├── userIsAdmin / userPermissions / userFieldMap
    └── shareIsAdmin / sharePermissions / shareFieldMap
    ↓
根据 Admin 状态决定合并策略
    ├── 都是 Admin → 完全访问
    ├── 用户 Admin 但角色非 Admin → 使用角色权限
    ├── 角色 Admin 但用户非 Admin → 使用用户权限
    └── 都非 Admin → 取交集 (intersection)
    ↓
生成关联访问权限
    └── traverse() → 递归生成关联集合的访问规则
    ↓
合并权限并返回
    ├── generatedPermissions: 自动生成的访问规则
    └── limitedPermissions: 原始权限过滤后
```

#### 1.1.2 核心代码解析

```typescript
// get-permissions-for-share.ts 核心逻辑
export async function getPermissionsForShare(
    accountability: Pick<Accountability, 'share' | 'ip'>,
    collections: string[] | undefined,
    context: Context,
): Promise<Permission[]> {
    
    // 1. 获取分享的基本信息
    const { collection, item, role, user_created } = await fetchShareInfo(accountability.share!, context);

    // 2. 构建两个 accountability
    // userAccountability: 分享创建者
    const userAccountability: Accountability = {
        user: user_created.id,
        role: user_created.role,
        roles: await fetchRolesTree(user_created.role, { knex: context.knex }),
        admin: false,
        app: false,
        ip: accountability.ip,
    };

    // shareAccountability: 分享指定的角色
    const shareAccountability: Accountability = {
        user: null,
        role: role,
        roles: await fetchRolesTree(role, { knex: context.knex }),
        admin: false,
        app: false,
        ip: accountability.ip,
    };

    // 3. 并行获取两者的权限信息
    const [
        { admin: shareIsAdmin },
        { admin: userIsAdmin },
        userPermissions,
        sharePermissions,
        shareFieldMap,
        userFieldMap,
    ] = await Promise.all([
        fetchGlobalAccess(shareAccountability, { knex: context.knex }),
        fetchGlobalAccess(userAccountability, { knex: context.knex }),
        getPermissionsForAccountability(userAccountability, context),
        getPermissionsForAccountability(shareAccountability, context),
        fetchAllowedFieldMap({ accountability: shareAccountability, action: 'read' }, context),
        fetchAllowedFieldMap({ accountability: userAccountability, action: 'read' }, context),
    ]);

    // 4. 根据 Admin 状态决定权限策略
    const isAdmin = userIsAdmin && shareIsAdmin;
    let permissions: Permission[] = [];
    let reducedSchema: SchemaOverview;

    if (isAdmin) {
        // 两者都是 Admin → 完全访问
        defaults.fields = ['*'];
        reducedSchema = context.schema;
    } else if (userIsAdmin && !shareIsAdmin) {
        // 创建者是 Admin，但分享角色不是 → 使用分享角色的权限
        permissions = sharePermissions;
        reducedSchema = reduceSchema(context.schema, shareFieldMap);
    } else if (shareIsAdmin && !userIsAdmin) {
        // 分享角色是 Admin，但创建者不是 → 使用创建者的权限
        permissions = userPermissions;
        reducedSchema = reduceSchema(context.schema, userFieldMap);
    } else {
        // 都不是 Admin → 取两者权限的交集
        permissions = mergePermissions('intersection', sharePermissions, userPermissions);
        reducedSchema = reduceSchema(context.schema, shareFieldMap);
        reducedSchema = reduceSchema(reducedSchema, userFieldMap);
    }
```

### 1.2 分享权限的决策矩阵

| 用户状态 | 分享角色状态 | 权限来源 | 字段访问 |
|---------|-------------|---------|---------|
| Admin | Admin | 完全访问 | `['*']` |
| Admin | 非 Admin | 分享角色权限 | 分享角色字段 |
| 非 Admin | Admin | 创建者权限 | 创建者字段 |
| 非 Admin | 非 Admin | 两者交集 | 字段交集 |

### 1.3 关联权限的自动生成（traverse 函数）

分享权限的一个关键特性是**自动生成关联数据的访问权限**。这通过 `traverse` 函数实现：

```typescript
export function traverse(
    schema: SchemaOverview,
    rootItemPrimaryKeyField: string,
    rootItemPrimaryKey: string,
    currentCollection: string,
    parentCollections: string[] = [],
    path: string[] = [],
): Partial<Permission>[] {
    const permissions: Partial<Permission>[] = [];

    // 防止循环引用（如 articles -> related_articles -> articles）
    if (parentCollections.includes(currentCollection)) {
        return permissions;
    }

    const relationsInCollection = schema.relations.filter((relation) => {
        return relation.collection === currentCollection || relation.related_collection === currentCollection;
    });

    for (const relation of relationsInCollection) {
        // 识别关系类型
        let type;
        if (relation.related_collection === currentCollection) {
            type = 'o2m';  // 一对多：当前集合是"多"的一方
        } else if (!relation.related_collection) {
            type = 'a2o';  // 多态关联
        } else {
            type = 'm2o';  // 多对一
        }

        // 根据关系类型生成不同的访问规则
        if (type === 'o2m') {
            // 一对多：通过外键关联到根项目
            permissions.push({
                collection: relation.collection,
                permissions: getFilterForPath(type, [...path, relation.field], rootItemPrimaryKeyField, rootItemPrimaryKey),
            });
            // 递归遍历
            permissions.push(...traverse(schema, rootItemPrimaryKeyField, rootItemPrimaryKey,
                relation.collection, [...parentCollections, currentCollection], [...path, relation.field]));
        }

        if (type === 'm2o') {
            // 多对一：通过外键追溯到关联项目
            permissions.push({
                collection: relation.related_collection!,
                permissions: getFilterForPath(type, [...path, `$FOLLOW(${relation.collection},${relation.field})`],
                    rootItemPrimaryKeyField, rootItemPrimaryKey),
            });
            // 递归遍历（如果有反向关系）
            if (relation.meta?.one_field) {
                permissions.push(...traverse(schema, rootItemPrimaryKeyField, rootItemPrimaryKey,
                    relation.related_collection!, [...parentCollections, currentCollection], [...path, relation.meta?.one_field]));
            }
        }
        // ... a2o 类似处理
    }

    return permissions;
}
```

## 2. 策略冲突时的优先级规则

### 2.1 策略获取的排序规则

**文件**: `api/src/permissions/lib/fetch-policies.ts`

策略的获取顺序决定了权限合并的优先级。Directus 采用**从低到高**的排序：

```typescript
export async function _fetchPolicies(
    { roles, user, ip }: Pick<Accountability, 'user' | 'roles' | 'ip'>,
    context: Context,
): Promise<string[]> {
    // ... 过滤 IP 后 ...

    /*
     * Sort rows by priority (goes bottom up):
     * - Parent role policies    (优先级最低)
     * - Child role policies     (优先级中等)
     * - User policies           (优先级最高)
     */
    filteredAccessRows.sort((a, b) => {
        // User policies (role 为 null) 排在最后（优先级最高）
        if (!a.role && !b.role) return 0;
        if (!a.role) return 1;   // a 是 user policy，排后面
        if (!b.role) return -1;  // b 是 user policy，排后面

        // 角色策略按 roles 数组顺序排列
        // roles 数组是从根到当前角色的顺序（父角色在前）
        return roles.indexOf(a.role) - roles.indexOf(b.role);
    });

    const ids = filteredAccessRows.map(({ policy }) => policy.id);
    return ids;
}
```

### 2.2 角色继承链（fetchRolesTree）

**文件**: `packages/utils/node/fetch-roles-tree.ts`

```typescript
export async function fetchRolesTree(start: string | null, context: { knex: Knex }): Promise<string[]> {
    if (!start) return [];

    let parent: string | null = start;
    const roles: string[] = [];

    // 从当前角色向上追溯到根角色
    while (parent) {
        const role = await knex
            .select('id', 'parent')
            .from('directus_roles')
            .where({ id: parent })
            .first();

        if (!role) break;

        roles.push(role.id);
        
        // 防止循环引用
        if (role.parent && roles.includes(role.parent)) {
            roles.reverse();
            throw new Error(`Recursion encountered: ${rolesStr}`);
        }

        parent = role.parent;
    }

    // 反转得到：[根角色, ..., 父角色, 当前角色]
    roles.reverse();
    return roles;
}
```

### 2.3 策略排序的完整示例

假设角色继承关系：`Public → Editor → Admin`，且用户 `user1` 有自己的策略：

```
roles 数组: ['public-role-id', 'editor-role-id', 'admin-role-id']

排序后策略顺序:
```

### 2.4 权限合并策略（mergePermissions）

**文件**: `api/src/permissions/utils/merge-permissions.ts`

#### 2.4.1 三种合并策略

```typescript
export function mergePermissions(
    strategy: 'and' | 'or' | 'intersection',
    ...permissions: Permission[][]
): Permission[] {
    
    if (strategy === 'intersection') {
        // 交集策略：只保留所有列表共有的 collection__action
        const permissionKeys = permissions.map((perms) => {
            return new Set(perms.map((p) => `${p.collection}__${p.action}`));
        });

        const intersectionKeys = permissionKeys.reduce((acc, val) => {
            return new Set([...acc].filter((x) => val.has(x)));
        }, permissionKeys[0]);

        // 先各自用 or 合并，再过滤，最后用 and 合并
        const deduplicateSubpermissions = permissions.map((perms) => {
            return mergePermissions('or', perms);
        });

        allPermissions = flatten(deduplicateSubpermissions).filter((p) => {
            return intersectionKeys.has(`${p.collection}__${p.action}`);
        });

        strategy = 'and';  // 交集内部使用 and 合并
    } else {
        allPermissions = flatten(permissions);
    }

    // 按 collection__action 分组合并
    const mergedPermissions = allPermissions
        .reduce((acc, val) => {
            const key = `${val.collection}__${val.action}`;
            const current = acc.get(key);
            acc.set(key, current ? mergePermission(strategy, current, val) : val);
            return acc;
        }, new Map())
        .values();

    return Array.from(mergedPermissions);
}
```

#### 2.4.2 单个权限的合并（mergePermission）

```typescript
export function mergePermission(
    strategy: 'and' | 'or',
    currentPerm: Permission,
    newPerm: Permission,
): Omit<Permission, 'id' | 'system'> {
    
    const logicalKey = `_${strategy}`;  // '_and' 或 '_or'

    let { permissions, validation, fields, presets } = currentPerm;

    // 合并 permissions 规则
    if (newPerm.permissions) {
        if (currentPerm.permissions && Object.keys(currentPerm.permissions)[0] === logicalKey) {
            // 已有的就是相同逻辑操作，追加
            permissions = {
                [logicalKey]: [
                    ...(currentPerm.permissions as any)[logicalKey],
                    newPerm.permissions,
                ],
            };
        } else if (currentPerm.permissions) {
            // 空对象 {} 在 OR 合并中表示"完全访问"，会覆盖其他规则
            if (strategy === 'or' && 
                (isEqual(currentPerm.permissions, {}) || isEqual(newPerm.permissions, {}))) {
                permissions = {};  // 完全访问
            } else {
                // 包装成逻辑操作
                permissions = {
                    [logicalKey]: [currentPerm.permissions, newPerm.permissions],
                };
            }
        } else {
            // 当前为空，直接用新的
            permissions = {
                [logicalKey]: [newPerm.permissions],
            };
        }
    }

    // validation 合并逻辑同上
    // ...

    // 字段合并
    fields = mergeFields(currentPerm.fields, newPerm.fields, strategy);

    // presets 使用对象合并（后面的覆盖前面的）
    if (newPerm.presets) {
        presets = merge({}, presets, newPerm.presets);
    }

    return omit({ ...currentPerm, permissions, validation, fields, presets }, ['id', 'system']);
}
```

#### 2.4.3 字段合并策略（mergeFields）

**文件**: `api/src/permissions/utils/merge-fields.ts`

```typescript
export function mergeFields(fieldsA: string[] | null, fieldsB: string[] | null, strategy: 'and' | 'or') {
    if (fieldsA === null) fieldsA = [];
    if (fieldsB === null) fieldsB = [];

    if (strategy === 'and') {
        // AND：取交集
        if (fieldsA.length === 0 || fieldsB.length === 0) return [];  // 任一方为空 → 无权限
        if (fieldsA.includes('*')) return fieldsB;  // A 是 *，以 B 为准
        if (fieldsB.includes('*')) return fieldsA;  // B 是 *，以 A 为准
        return intersection(fieldsA, fieldsB);
    } else {
        // OR：取并集
        if (fieldsA.length === 0) return fieldsB;
        if (fieldsB.length === 0) return fieldsA;
        if (fieldsA.includes('*') || fieldsB.includes('*')) return ['*'];  // 任一方有 * → 完全访问
        return union(fieldsA, fieldsB);
    }
}
```

### 2.5 合并策略应用场景

| 场景 | 合并策略 | 说明 |
|------|---------|------|
| 同一用户的多策略 | `or` | 任一策略满足即可 |
| 分享权限（用户∩角色） | `intersection` → `and` | 两者都必须满足 |
| 分享权限最终合并 | `and` | 角色权限 AND 项目限制 |
| 关联权限合并 | `or` | 任一关联路径可达即可 |

### 2.6 权限规则中的特殊值

#### 2.6.1 空对象 `{}` 的特殊含义

在权限规则中，`permissions: {}` 表示**完全访问**：

```typescript
// 例子：两个权限规则 OR 合并
const perm1 = { permissions: { status: { _eq: 'published' } } };
const perm2 = { permissions: {} };  // 完全访问

// 合并结果（OR 策略）
const merged = mergePermissions('or', [perm1], [perm2]);
// 结果: { permissions: {} }  —— 因为 {} 在 OR 中会覆盖其他规则
```

#### 2.6.2 `null` vs `[]` vs `['*']`

| 值 | 字段权限含义 | permissions 含义 |
|---|-------------|-----------------|
| `null` | 未指定（可能继承） | 无限制（完全访问） |
| `[]` | 无字段权限 | 无项目（空集合） |
| `['*']` | 所有字段 | 不适用 |

### 3.2 各阶段决策的相互影响

#### 3.2.1 全局 Admin 的短路效应

```typescript
// processAst.ts 中的短路
if (!options.accountability || options.accountability.admin) {
    // 只验证字段存在性，不验证权限
    for (const [path, { collection, fields }] of [...fieldMap.read.entries(), ...fieldMap.other.entries()]) {
        validatePathExistence(path, collection, fields, context.schema);
    }
    return options.ast;  // 直接返回，不注入权限
}

// validateAccess.ts 中的短路
if (options.accountability.admin === true) {
    return;  // 直接通过，不检查
}
```

**影响**：`admin=true` 会导致：
1. `processAst` 不注入 `cases` 和 `whenCase`
2. `validateAccess` 直接通过
3. `fetchPermissions` 可能被跳过

#### 3.2.2 策略排序对合并结果的影响

虽然 `mergePermissions` 的 `and`/`or` 逻辑是数学上可交换的，但**预设值（presets）的合并不是**：

```typescript
// presets 使用 lodash.merge，后面的覆盖前面的
if (newPerm.presets) {
    presets = merge({}, presets, newPerm.presets);
}
```

**示例**：

```
策略顺序：PolicyA → PolicyB → PolicyC (用户策略)

PolicyA presets: { status: 'draft', author: 'default' }
PolicyB presets: { status: 'published' }
PolicyC presets: { category: 'news' }

合并结果: { status: 'published', author: 'default', category: 'news' }
// 注意：PolicyB 的 status 覆盖了 PolicyA，但用户策略没有 status
```

#### 3.2.3 分享操作的双重验证

分享操作中，权限决策发生在两个层面：

```
分享请求
    ↓
authenticate 中间件
    ↓  accountability.share = 'share-token'
fetchPermissions()
    ↓
检测到 accountability.share
    ↓
getPermissionsForShare()
    ├── fetchShareInfo() → 获取 collection, item, role, user_created
    ├── 构建 userAccountability (创建者) 和 shareAccountability (角色)
    ├── 分别获取两者的权限
    ├── 根据 admin 状态选择策略（交集/使用某一方）
    ├── traverse() 生成关联访问规则
    └── 合并：角色权限 AND 项目限制
    ↓
返回最终权限
```

### 3.3 权限决策的优先级汇总

| 优先级 | 决策点 | 影响范围 | 说明 |
|-------|--------|---------|------|
| **1（最高）** | `accountability.admin` | 全局 | 跳过所有权限检查 |
| **2** | IP 过滤 (`filterPoliciesByIp`) | 策略级别 | IP 不在白名单的策略被排除 |
| **3** | 策略排序 | 权限合并顺序 | 父角色 → 子角色 → 用户 |
| **4** | 合并策略 (`and`/`or`) | 规则逻辑 | AND 更严格，OR 更宽松 |
| **5** | 空对象 `{}` | 完全访问 | OR 合并时覆盖其他规则 |
| **6** | 字段合并 | 字段级 | AND 取交集，OR 取并集 |
| **7** | Presets 合并 | 预设值 | 后面的覆盖前面的 |

### 3.4 典型决策场景分析

#### 场景 1：用户有多个角色

```
用户: user1
角色: roleA (父) → roleB (子，当前角色)

roles 数组: ['roleA-id', 'roleB-id']

策略获取顺序:
1. roleA 的策略（优先级低）
2. roleB 的策略（优先级中）
3. user1 的个人策略（优先级高）

权限合并策略: OR
- 任一角色有权限即可访问
- 字段取并集
- presets 后面的覆盖前面的
```

#### 场景 2：分享操作（用户和角色都非 Admin）

```
分享创建者: 有 articles:read 权限，条件 { author: { _eq: $CURRENT_USER } }
分享角色: 有 articles:read 权限，条件 { status: { _eq: 'published' } }

权限合并策略: intersection → and

1. 先检查 collection__action 交集
   - 两者都有 articles:read → 保留

2. 用 AND 合并规则
   { _and: [
       { author: { _eq: 'creator-id' } },
       { status: { _eq: 'published' } }
   ]}

3. 加上分享项目限制
   { _and: [
       { _and: [...] },  // 上面的合并结果
       { id: { _eq: 'shared-item-id' } }
   ]}

最终可访问的文章必须同时满足:
- 作者是分享创建者
- 状态是 published
- ID 是分享的项目
```

#### 场景 3：一个策略完全访问，一个有限制

```
策略 A: permissions: {}  (完全访问)
策略 B: permissions: { status: { _eq: 'published' } }

OR 合并结果: permissions: {}  (完全访问，因为 {} 会覆盖)

AND 合并结果: { status: { _eq: 'published' } }  (有限制)
```

## 5. 总结

### 5.1 核心设计原则

1. **分层决策**：从全局 Admin 检查到具体字段权限，逐层过滤
2. **短路优化**：Admin 用户跳过大部分权限检查，提升性能
3. **灵活合并**：支持 `and`/`or`/`intersection` 三种策略，适应不同场景
4. **关联遍历**：分享操作自动生成关联数据的访问规则
5. **优先级明确**：用户策略 > 子角色 > 父角色

### 5.2 常见坑点

1. **空对象 `{}` 的特殊含义**：在 OR 合并中表示完全访问，会覆盖其他限制
2. **Presets 的顺序敏感**：后面的策略会覆盖前面的预设值
3. **分享操作的双重限制**：用户和角色权限取交集，再与项目限制取 AND
4. **IP 过滤的严格性**：IP 未知时，有 IP 限制的策略会被排除

### 5.3 调试建议

1. 检查 `accountability.admin` 是否为 `true`（可能意外跳过权限）
2. 验证 `fetchPolicies` 返回的策略顺序是否符合预期
3. 确认 `mergePermissions` 使用的策略（`and`/`or`/`intersection`）
4. 对于分享操作，检查 `userAccountability` 和 `shareAccountability` 的权限交集
